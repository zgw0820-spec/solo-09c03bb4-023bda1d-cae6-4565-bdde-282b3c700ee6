# 边缘网关值班切换 Demo

FastAPI + SQLite 实现的边缘网关与操作网页。值班员切换处理较久的 HTTP 服务上游、
或替换某上游的服务地址时，已接纳的请求仍从**接单时生效的目标与地址**取回完整响应；
新请求在确认切换/地址更新后立即走新目标、新地址。

## 组成

| 组件 | 说明 |
| --- | --- |
| `gateway/` | FastAPI 网关：转发请求、操作 API、值班台网页（`/`）、SQLite 持久化 |
| `upstream/` | 演示上游：可设默认响应延迟（`DEFAULT_DELAY_MS`），请求参数 `delay_ms` 可覆盖；`/health` 供切换前探测；`/admin/work_mode` 可让 `/work` 运行时故障 |
| `docker-compose.yml` | 一键启动**两个网关实例**（共用同一 SQLite 库）+ 三个本地上游（alpha 默认 3s、替换用新节点 alpha2 默认 0.4s、beta 默认 0.5s） |
| `scripts/` | 本地（无 Docker）端到端验证脚本 |

## 运行

Docker Compose：

```bash
docker compose up --build
# 值班台网页: http://localhost:8080/  (gateway-1)
#             http://localhost:8081/  (gateway-2，与 gateway-1 共用路由库)
```

本地直接跑（无需 Docker，含自动化断言与重启演练）：

```bash
./scripts/run_local.sh
```

### 演示：替换 alpha 的服务地址

1. 在 `http://localhost:8080/`（gateway-1）发一个延迟 3000ms 的请求，
   它出现在“在途请求明细”中，绑定当时的地址 `http://upstream-a:8000`。
2. 在 `http://localhost:8081/`（gateway-2）的“替换上游地址”面板把
   `alpha` 的地址改为 `http://upstream-a2:8000` 并提交。
3. 回到 gateway-1 再发一个请求：日志显示它由**新地址**（实际响应节点
   `alpha2`）返回；而第 1 步的在途请求仍从**旧地址**（节点 `alpha`）
   取回完整响应——接单先于地址更新的请求绝不错投到新节点。

## 语义与实现要点

- **接单即快照目标与地址**：`/api/call` 在接纳时于同一把锁、同一事务里
  快照当前路由目标**及其登记地址**并登记在途（`db.admit` 联表读取 +
  写入在途）。随后无论路由切换还是地址被另一实例替换，该请求都从快照
  地址取回完整响应；更新前接单的仍访问旧地址，更新后接单的走新地址。
- **旧地址故障不偷偷改投**：转发只打向快照地址，失败即返回 502/上游
  状态码，绝不重新解析登记、绝不改投新地址。
- **地址替换立即生效**：`POST /api/upstreams/update` 改写登记并令路由
  版号 +1，不等待旧请求结束；此后接纳的请求立即走新地址。地址未变化
  的更新是空操作（版号不变）。
- **先探测后确认**：`POST /api/switch/probe` 只探测候选（`/health` + `/work`），
  从不改写路由——探测期间请求继续走旧目标，探测失败维持原路由；
  `POST /api/switch/commit` 才把路由切到新目标。
- **版号防交错**：网页每次操作都携带它所见的路由版号；确认切换按
  `version = base_version` 做比较并交换（CAS）。切换与地址替换都会推进
  版号，因此交错的确认（含迟到探测发起的确认、被地址替换超越的确认）
  收到 `409 version_conflict`，不得覆盖已生效路由。
- **可下线提示**：非当前目标的在途数清零时，状态接口给出 `can_offline: true`，
  网页对应行显示“可下线 ✓”。
- **双实例共库**：两个网关实例共用同一 SQLite 库。在途记录按实例归属
  （`GATEWAY_INSTANCE`），启动时只清理**本实例**遗留的中断在途，不会抹掉
  幸存实例的在途视图（清理条数在网页顶部展示）。
- **重启恢复**：路由与上游登记在 SQLite 中持久化。上游登记仅首次启动
  从环境变量播种，此后以库为准——值班员替换的地址不会因重启被悄悄还原；
  重启后按已登记路由接流量。

## 操作 API

| 方法/路径 | 说明 |
| --- | --- |
| `GET /api/state` | 当前路由（目标+版号）、各上游登记地址与在途数、在途明细（含接单快照地址与所属实例）、最近探测 |
| `POST /api/call` | 发起转发请求 `{delay_ms?, path?}`，返回服务目标、**实际使用的地址**与上游响应 |
| `POST /api/upstreams/update` | 替换上游地址 `{name, url}`：更新前接单的仍走旧地址，更新后接单的走新地址；版号 +1 |
| `POST /api/switch/probe` | 探测候选 `{target, base_version}`，不改路由 |
| `POST /api/switch/commit` | 确认切换 `{target, base_version, probe_id}`，版号冲突返回 409 |

演示/测试旋钮：`GATEWAY_ADMIT_DELAY_MS` 可人为拉大“接单→发出”的交错
窗口（默认 0），便于在网页上或测试里复现接单与地址更新的交错。

## 验证

`scripts/run_local.sh` 启动三个上游与**两个共用同一 SQLite 库的网关**，
执行 `scripts/smoke_test.py` 两阶段共 49 项断言：跨实例地址替换与接单
交错（更新前接单走旧地址、更新后接单走新地址、旧地址故障只报错不改投）、
切换语义、探测失败维持路由、交错切换版号冲突、慢请求从原上游取回完整
响应、在途清零才可下线、`kill -9` 后重启的在途清理、路由/版号/替换后
地址的保持。
